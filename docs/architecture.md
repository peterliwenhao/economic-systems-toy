# 协作架构

## 核心边界

本模板管理的是共享项目状态，不托管个人 Codex 对话。每位成员在自己的 clone、分支或 worktree 中工作；团队通过 Issue、PR、文档和实验 manifest 交换可审查成果。

```text
项目知识 ──→ GitHub 任务 ──→ 成员 + 个人 Codex
    ↑              │                 │
    │              └── 依赖/验收 ────┤
    │                                ↓
决定/会议 ←── 评审 ←── Pull Request + 实验证据
```

## 单一事实源

- GitHub Issues/Projects 管任务状态；Dashboard 不提供第二套编辑入口。
- 主分支决定代码是否生效；个人 worktree 和未合并分支不是团队基线。
- 合并后的决策文档代表团队确认内容；会议草稿必须区分提议与决定。
- 实验 manifest 只记录元数据和产物链接；大型结果由外部存储保管。

## 为什么第一版不使用数据库

对于 2–5 人团队，GitHub 已经提供身份、并发编辑、审计、通知和 PR 权限。再增加 SQLite 或自建服务会制造同步、备份、认证和部署责任，而且多数本地代理看板不支持多台电脑并发共享同一个数据库。

## 对现有开源项目的借鉴

- **hivemind（MIT）**：借鉴 Markdown 可读任务、验收项、活动日志和 MCP 工具边界；未复制代码，也不绑定其 Electron/MCP 运行时。
- **ATC Kanban（MIT）**：借鉴明确状态机、依赖验证和未来原子领取语义；第一版没有复制其 SQLite、WebSocket 或锁实现。
- **Kangentic / Plane（AGPL-3.0）**：只参考交互和工作流概念，不复制代码，从而避免模板被其实现和许可证耦合。
- **Vibe Kanban（Apache-2.0）**：借鉴 worktree→review→PR 生命周期；不依赖其已经变化的云端团队功能。
- **DVC / MLflow（Apache-2.0）**：作为可选工具直接集成，不重写数据版本或实验追踪能力。

本模板的 Dashboard 和脚本是独立实现。若将来复制第三方代码，必须同时记录来源、版本、许可证、修改范围和 NOTICE 要求。

## 扩展顺序

1. 先使用当前模板运行真实任务。
2. 数据或权重开始阻碍复现时接入 DVC。
3. runs 数量需要集中比较时接入 MLflow。
4. 重复领取成为真实问题时增加 MCP + 服务端原子锁。
5. 需要从页面启动代理时集成成熟执行器，而不是自行实现 PTY、会话恢复和权限代理。

# 受控提案双人评审工作流

- 工作流状态：可在需要时直接采用；
- 适用对象：需要先经过核心评审，再成为团队正式工作基础的修改；
- 必需评审人：张馨月、刘充；
- 正式开放节点：修改合入 `dev`；
- 当前自动化状态：尚未配置专用 GitHub Actions 和分支规则。

## 一、工作流目的

当李文浩或其他成员提出一项可能影响研究方向、整体架构、经济机制、模块边界或后续多人工作的修改时，可以先将其作为受控提案提交给张馨月和刘充评审。两位评审人均确认后，提案才合入团队的集成分支，并通知其他成员开始采用。

这里的“开放”表示成为团队可以依赖的正式基线。提案分支和 Pull Request 在评审期间可能对仓库协作者可见，但其他成员不应基于其中尚未批准的内容开展后续工作。

## 二、适用情况

出现下列情况之一时，可以采用本工作流：

- 修改项目整体研究方向或核心问题；
- 修改五个子系统的职责、边界或主要调用关系；
- 修改多个成员都需要依赖的公共接口或公共数据对象；
- 修改市场、Lange、Cockshott 或劳动配置机制的核心经济含义；
- 修改会影响后续实验可比性的世界规则、信息条件或实验设计；
- 提案人明确要求先完成核心评审，再让其他成员采用。

普通的局部实现、文案修正、测试补充和不影响他人的模块内部重构，可以继续使用日常 Pull Request 流程。

## 三、角色分工

| 角色 | 责任 |
|---|---|
| 提案人 | 说明修改目的、影响范围、未决问题和验证情况；根据评审意见修改提案 |
| 张馨月 | 从项目推进、整体架构、模块集成和工程可执行性角度审阅 |
| 刘充 | 从经济理论、制度含义、行为假设和实验解释角度审阅 |
| 相关模块负责人 | 必要时补充接口或实现影响，但不代替两位必需评审人批准 |
| 其他成员 | 评审期间可以了解提案，不以提案分支作为正式开发基线；合入 `dev` 后再采用 |

## 四、标准流程

### 第一步：声明采用本工作流

提案人在任务或 Pull Request 开头注明：

```text
工作流：受控提案双人评审
必需评审人：张馨月、刘充
正式开放条件：两人均批准并合入 dev
```

### 第二步：从集成分支建立提案分支

```bash
git switch dev
git pull --ff-only origin dev
git switch -c proposal/<owner>-<topic>
```

示例：

```text
proposal/liwenhao-world-architecture-v2
```

如果项目当时尚未建立 `dev`，由张馨月先指定本轮使用的集成分支，并在 Pull Request 中明确记录；不能自行把 `main` 当作临时评审分支。

### 第三步：提交受控提案 Pull Request

Pull Request 的目标分支为 `dev`，标题建议使用：

```text
[GATED PROPOSAL] <修改主题>
```

PR 描述至少包含：

```markdown
## 修改目的

## 主要变化

## 影响的模块和成员

## 希望张馨月重点审阅的问题

## 希望刘充重点审阅的问题

## 尚未确定的问题

## 已完成的验证

## 正式开放后的下一步
```

PR 在准备完整之前保持为 Draft。转为 Ready for review 后，同时请求张馨月和刘充审阅。

### 第四步：完成双人评审

合入前必须同时满足：

- 张馨月的最新有效审阅状态为 `APPROVED`；
- 刘充的最新有效审阅状态为 `APPROVED`；
- 必需的自动检查通过；
- 阻塞性讨论已经解决；
- PR 中列出的文档、代码和接口保持一致。

如果批准后又加入会改变实际内容的新 commit，两位评审人需要重新确认最新版本。单纯解决合并冲突且没有改变提案含义时，也应在 PR 中说明具体处理内容。

如果某位必需评审人同时是提案作者，他不能批准自己的 PR。此时应在开始评审前由张馨月和李文浩共同指定替代评审人，并把原因与替代人记录在 PR 中。

### 第五步：合入并正式开放

两位评审人均批准且检查通过后，由张馨月或项目指定的集成人将 PR 合入 `dev`。合入后：

1. 在对应任务或会议记录中写明已经通过双人评审；
2. 通知受影响的成员该修改已经成为正式基线；
3. 相关成员从最新 `dev` 新建分支，或把自己的未完成分支更新到最新 `dev`；
4. 更新受到影响的正式架构、接口或任务文档；
5. 删除已经合入且不再需要的远端提案分支。

其他成员不得直接从尚未合入的 `proposal/*` 分支继续开发。

## 五、状态定义

| 状态 | 含义 | 其他成员是否可以作为基线使用 |
|---|---|---|
| `DRAFT` | 提案人仍在整理 | 否 |
| `IN_REVIEW` | 已请求张馨月和刘充审阅 | 否 |
| `CHANGES_REQUESTED` | 至少一位评审人要求修改 | 否 |
| `APPROVED` | 两位评审人均批准，等待检查或合入 | 暂不使用 |
| `MERGED_TO_DEV` | 已合入集成分支并完成通知 | 是 |
| `CLOSED` | 提案撤回或未被采用 | 否 |

## 六、建议的 GitHub 强制措施

需要把本流程升级为自动强制时，可以增加以下配置：

1. 保护 `dev`，要求所有修改通过 Pull Request；
2. 禁止直接 push、force push 和删除 `dev`；
3. 启用自动测试与文档验证；
4. 启用新 commit 使旧批准失效；
5. 增加名为 `required-core-reviewers` 的 GitHub Actions 检查；
6. 让该检查确认张馨月和刘充的最新审阅均为 `APPROVED`；
7. 将 `required-core-reviewers` 设置为合入 `dev` 前的必需状态检查。

只设置“两人批准”不能保证批准者一定是张馨月和刘充；把两人同时写进同一条 `CODEOWNERS` 规则，也通常只需要其中一位批准。因此，严格执行指定双人评审时，应使用专门的检查工作流。

本节只记录未来配置方案。没有实际建立 GitHub Actions 或分支保护前，张馨月负责在合入时人工核对两位评审人的批准状态。

## 七、快速检查清单

### 提案人

- [ ] 从 `dev` 新建 `proposal/*` 分支；
- [ ] PR 标明采用受控提案双人评审工作流；
- [ ] 分别列出希望张馨月和刘充审阅的问题；
- [ ] 说明影响的成员、接口、配置和实验；
- [ ] 根据意见完成修改并报告验证结果；
- [ ] 新 commit 推送后重新请求必要评审。

### 合入负责人

- [ ] 张馨月已经批准最新版本；
- [ ] 刘充已经批准最新版本；
- [ ] 自动检查通过；
- [ ] 阻塞性讨论解决；
- [ ] PR 已合入 `dev`；
- [ ] 已通知受影响成员正式采用；
- [ ] 正式文档和任务状态已经更新。
